[2026-07-21] Fixed feature collection gap (BUG #1, BUG #2)
-----------------------------------------------------------
What: Implemented live collection for directory_enumerated,
apistats, and dll_loaded (previously always 0), and fixed the
file-deletion mislabeling. Full technical detail in
bugs_debugs.txt BUG #1 / BUG #2.

Why this order: Retraining or threshold-tuning before fixing
feature collection would have been pointless - any model trained
would still receive a 41%-degraded feature vector at inference
time. Collection had to be correct first.

Design choice - proxies instead of true API hooking:
The original dataset's apistats/directory_enumerated came from
Cuckoo Sandbox's in-VM API hooking (true API call interception).
Replicating that on a live Windows host would require kernel-level
instrumentation (ETW consumer, minifilter driver) which is out of
scope given the time crunch for this paper. Instead:
  - apistats -> proxied by counting loaded cryptography-related
    DLLs (advapi32.dll, bcrypt.dll, crypt32.dll, ncrypt.dll,
    wintrust.dll) via psutil's memory_maps().
  - directory_enumerated -> proxied by counting distinct parent
    directories among a process's currently open files
    (psutil.Process.open_files()).
  - dll_loaded -> not a proxy, this is now a real, accurate count
    (len(proc.memory_maps())).

This is a deliberate, documented engineering trade-off appropriate
for a research prototype: it moves these features from "always
zero" (structurally blind) to "directionally meaningful" (present
and correlated with the underlying suspicious behavior), which is
a large improvement, while being honest that it is not a 1:1
reproduction of the original Cuckoo signal. This asymmetry between
training-time and live-time feature semantics is worth stating
explicitly as a limitation in the paper - it's a genuine, defensible
research finding, not just an implementation detail.

Consequence for retraining (see task #4): Because the E/L
(ransomware) rows in datasets/ransomware_dataset.csv /
balanced_dataset.csv still hold true Cuckoo-hooked apistats and
directory_enumerated values, and our live proxy cannot produce
values on that same scale, retraining on the unchanged dataset
means the model will still expect larger apistats/directory_enumerated
values than the live system can realistically produce for these two
features specifically. This is documented as a residual limitation.
Two ways to fully close it (both out of scope for now, listed as
future work): (a) implement real API hooking, or (b) regenerate
ransomware training rows using the same proxy method used for
normal_activity.csv so units match exactly on both sides.

[2026-07-21] Found and fixed a second, deeper bug in the same
feature pipeline (BUG #3): birth-time-only sampling
-----------------------------------------------------------
While auditing for remaining false positive/negative sources
(priority #3), pulled real per-class statistics from
datasets/balanced_dataset.csv to sanity-check the BUG #1 fix
against the actual training distribution (see bugs_debugs.txt
BUG #3 for the full numbers). Finding: dll_loaded, apistats, and
directory_enumerated are strongly discriminating features when
populated (ransomware classes sit far above goodware on all three
in the real training data), which confirmed BUG #1 was worth fixing
- but also exposed that the original implementation only sampled a
process ONCE, at the exact moment it was first observed, before it
has typically loaded its own dependencies or opened any files. This
would have made the BUG #1 fix nearly ineffective in practice for
any ransomware running as a single long-lived process (which is the
realistic case, not many short-lived child processes).

Fixed by re-sampling every tracked process every poll cycle (2s) and
emitting the delta since last cycle, so a process's behavior
accumulates properly across the 30-second aggregation window instead
of being frozen at its first instant. Full detail in bugs_debugs.txt
BUG #3.

Methodological note for the paper: this is a good example of why
checking a fix against the *actual* training distribution (not just
"is the code no longer hard-zero") matters - the first fix was
technically correct but would have been empirically almost useless
without this second pass. Worth a sentence in the paper's methodology
or discussion section.

Performance note: this trades some CPU (memory_maps()/open_files()
calls now run every cycle for every tracked process, not just new
ones) for correctness. Flagged for the performance pass (task #6) to
revisit if it proves too costly on the target machine - candidate
mitigations if needed: sample only processes with recent file/network
activity, or increase the poll interval for the resampling pass
specifically.

[2026-07-21] Reprocessing hit a scalability bug (BUG #4), fixed
-----------------------------------------------------------
First attempt to reprocess events.csv (1.3 GB) crashed with
MemoryError - the script loaded every row into a Python list before
doing any aggregation. Rewrote as a single streaming pass (see
bugs_debugs.txt BUG #4) that only ever holds the current 30-second
window's counts plus the list of already-closed window samples in
memory, not the raw event stream. Also deduplicated the per-event
feature-counting logic into one _apply_event_to_counts() helper
(previously copy-pasted twice in the file, which is incidentally how
BUG #2 existed in two places instead of one).

Methodological note for the paper: this is a legitimate, citable
engineering constraint worth a line in the paper - real-world
continuous host monitoring produces event volumes that make
naive "load it all into memory" preprocessing approaches
non-viable, which is a genuine (if mundane) difference between
academic sandbox-run datasets (one row per sample) and live
telemetry-based ones (unbounded event streams that must be
processed incrementally).

[2026-07-21] Wired up the prevention system (priority #4) (BUG #5)
-----------------------------------------------------------
Found src/prevention_system.py implements process termination,
filesystem locking, network isolation, and Controlled Folder Access
automation, but was dead code - never imported or called from
anywhere except its own test block. CRITICAL alerts had no automated
response path at all. Wired PreventionSystem into
monitor/alert_system.py: AlertSystem now instantiates it and calls
handle_critical_alert() whenever a CRITICAL alert fires. See
bugs_debugs.txt BUG #5 for the exact change and the smoke test that
confirmed it initializes correctly.

Deliberately left prevention.enabled=false (config.json default,
unchanged) - did NOT flip it on or exercise auto-terminate /
network-isolation live, since those are destructive, machine-wide
actions. That is the user's call to make and test explicitly on a
machine/VM where a wrong termination or network drop is acceptable
collateral, not something to do silently while working on the
detection pipeline.

Known remaining gap: PreventionSystem.check_early_warning_indicators()
is also still dead code (defined, never called). Wiring it in would
mean calling it once per aggregation window from
monitor/start_monitoring.py and deciding what to do with returned
warnings (e.g. a WARNING-level alert path separate from the ML
classification path). Left as documented future work - the explicit
ask was auto-termination/quarantine on CRITICAL alerts, which is now
functional; early-warning heuristics are a smaller, separate feature.

Overall assessment for the paper: the fixes in this session (BUG #1
through #6) target CORRECTNESS of the deployed system (making live
inputs actually match what the model expects) rather than raw
offline benchmark accuracy, and offline accuracy alone does not
capture that improvement - it was already high before (98.43%) partly
because it was being measured in a self-consistent bubble that the
live system could never actually produce as input. The more important
claims to make in the paper are qualitative/architectural: 41% of the
model's decision weight was unreachable in production before this
session (BUG #1), a second-order sampling bug would have neutered
even a naive fix (BUG #3), and a coupled threshold would have caused
a false-alarm flood after any future retrain if not caught (BUG #6).
These are the kind of findings a rigorous methodology section should
highlight, arguably more valuable to the paper than the accuracy
numbers themselves.

[2026-07-21] Performance pass (task #6) (BUG #7)
-----------------------------------------------------------
Scope: light-touch, given this was explicitly the lowest priority
item and detection-accuracy work already consumed most of the

Two fixes in monitor/process_monitor.py, both detailed in
bugs_debugs.txt BUG #7:
  1. cpu_percent(interval=0.1) was blocking the poll loop 100ms per
     newly-seen process, for a value (cpu_usage) that is never
     actually read by the ML pipeline - only logged. Switched to the
     non-blocking form.
  2. The BUG #3 fix's per-cycle re-sampling of memory_maps()/
     open_files() for every tracked process now runs every OTHER
     poll cycle (~4s) instead of every cycle (~2s), halving that
     cost while still giving ~7-8 delta samples per process across
     a 30-second window - still far better than the original
     once-at-birth sampling.

Not done (explicitly out of scope given time budget): a live
benchmarked run to measure actual CPU/latency improvement, and
broader review of network_monitor.py/registry_monitor.py polling
costs. If the paper needs a performance section, running the
monitor for a fixed period before/after these two changes and
comparing CPU% (e.g. via Task Manager or psutil.cpu_percent() on the
python process itself) would produce a concrete number - flagged as
a possible follow-up, not done here.

[2026-07-21] Performance benchmark caught a critical regression
(BUG #9) - fixed before writing performance claims into the paper
-----------------------------------------------------------
Ran a real benchmark (266 processes on this machine, matching how
process_monitor.py actually queries them) instead of assuming BUG #7's
frequency-only mitigation was sufficient. Result: a full resampling
pass took ~52 SECONDS on average - 13-26x longer than the ~2-4s
interval it was supposed to run within. Profiling isolated the cause
to psutil.Process.open_files() (used only by directory_enumerated's
proxy), which averages ~148ms/process on Windows vs ~18ms/process for
memory_maps() (used by dll_loaded/apistats) - about 8x more expensive
per call, because Windows has no cheap equivalent to Linux's
/proc/pid/fd listing for enumerating open file handles.

This would have been a severe, SILENT regression if shipped: the
monitor would run without crashing or erroring, but would never
actually keep its polling interval, starving new-process detection
and defeating the entire point of BUG #3's continuous-resampling fix
(potentially back down to ~0-1 samples per 30s window in practice,
no better than the original bug). Full detail and the fix (removed
open_files()/directory_enumerated from the continuous resampling
loop entirely - it now only samples at process birth, same limitation
as before BUG #3 for this one feature; widened the remaining
dll_loaded/apistats resampling interval from BUG #7's guessed ~4s to
a measured, headroom-safe ~8s; added a cost-free supplementary
directory_enumerated signal from file_monitor.py's existing
watchdog-based, event-driven file activity - distinct directories
touched, which is free because file_monitor never polls) is in
bugs_debugs.txt BUG #9.

This is arguably the single most important methodological lesson from
this entire session, worth its own paragraph or even a short
subsection in the paper: a performance fix (BUG #7) that reduces call
FREQUENCY without measuring the call's actual COST under realistic
load can still leave the system fundamentally broken. The fix looked
complete after BUG #7 (code review would not have caught this - it
required running a benchmark against a real process count). Not
retraining the models again for this fix - it only changes HOW LIVE
DATA IS COLLECTED going forward (making the collection loop
responsive again), not the meaning of any trained feature; the models
retrained in the "final retrain" section above remain the ones to
report in the paper.

[2026-07-21] Investigated the encryption-ransomware recall gap
(92.75%) - two honest null results
-----------------------------------------------------------
User asked to "fix" the 92.75% class-E recall gap. Tried two standard,
legitimate levers, both using the same 10-fold CV framework for a
fair comparison against the documented baseline:

1. Class-weighted training (sklearn compute_sample_weight('balanced')
   passed to XGBoost.fit()): E recall moved from 92.75% to 92.87% -
   a +0.12 percentage point change, well within the fold-to-fold
   standard deviation (0.68-0.73%) already measured for this dataset.
   Not a real effect - noise.

2. Classification threshold sweep (the actual deployable knob in
   config.json, currently 0.85): using out-of-fold predicted
   probabilities from the same 10-fold CV, swept threshold from 0.85
   down to 0.30. E recall moved from 92.50% to only 93.00% at the
   MOST permissive threshold tested (0.30) - essentially flat across
   the entire range, while goodware false-alarm rate stayed
   negligible throughout (0.05% at worst).

reportable result. If the model's errors on class E were "borderline"
cases sitting just under the 0.85 confidence threshold, lowering the
threshold would have recovered many of them - it did not, even at a
threshold as low as 0.30. This means the ~58/800 misclassified E
samples are being classified as goodware with genuine (not
marginal) confidence - the model isn't uncertain about them, it is
confidently wrong. That points to a feature/data limitation (these
particular E samples' behavioral signature genuinely resembles
goodware in the current 12-feature representation) rather than a
calibration problem, and is NOT fixable by adjusting weights or
thresholds. Left as an honestly-reported limitation rather than
forcing an illusory fix - this is more scientifically useful for the
paper than a marginal-and-fake improvement would have been. Real
fixes would require either more/different E-class training data or
better features (e.g. real API hooking instead of the current
apistats proxy - see BUG #1's caveat) - both flagged as future work.

[2026-08-12] v2 evaluation audit: corrects the headline accuracy,
the autoencoder F1, and the live-demo narrative - all three numbers

-----------------------------------------------------------
Follow-up work, independent of the 2026-07-21/22 sessions above.
Re-examined the evaluation methodology itself (not the models or the
live-collection code) and found three of this project's most-quoted
results were measuring something other than what they claimed to.
Full technical detail in bugs_debugs.txt BUG #13 and in
results/data_quality.json, results/cross_validation_grouped.json,
results/autoencoder_variance.json, results/negative_control.json - this
entry is the narrative summary for the paper.

IMPORTANT: the deployed model files (models/practical_xgboost.pkl,
models/autoencoder_model.keras) were NOT retrained or modified in this
pass - both are still dated 2026-07-22, from the "TRUE FINAL retrain"
entry above. Everything in this entry is a RE-EVALUATION of that same
static balanced_dataset.csv using corrected methodology, run on
temporary, in-memory models trained fresh for each CV fold / each seed
and discarded afterward - not a change to what ships.

1. HEADLINE ACCURACY WAS LEAKAGE-INFLATED (supersedes the 98.10% figure
   throughout this file and please_study_this.txt Section 8)

   results/data_quality.json quantifies why: projecting the 50-feature
   source dataset down to the 12 features this project can actually
   collect live collapses class separation hard. The SOURCE dataset is
   fine at 50 features (1750/2000 rows distinct); at the 12-feature
   projection, goodware alone collapses from 1000 sandboxed executions
   to 117 distinct vectors. Across the full 2999-row balanced_dataset.csv,
   61.5% of rows (1844/2999) share an exact 12-feature vector with at
   least one other row. src/cross_validate_xgboost.py's
   StratifiedKFold(shuffle=True) treats every row as independent, so
   most of a duplicated row's twins land in the training folds under
   shuffling - the held-out copy is memorised, not generalised to.

   scripts/cross_validate_grouped.py re-ran cross-validation with
   StratifiedGroupKFold, grouping by the exact 12-feature vector (the
   model's actual input - not a hash of the 50-column source row, which
   would under-group and still leak). Zero group-leakage violations
   confirmed programmatically across all 10 folds.

   RESULT: mean accuracy 85.59% (std 15.39%, range 43.88%-100% across
   folds) - down from 98.10%. Aggregate confusion matrix (order E/G/L):
     E: [674,  76,  50]
     G: [245, 1754,  0]   <- G misclassified as E: ~0 before, 12.3% now
     L: [ 50,  11, 139]   <- L precision/recall both fell from
                              near-perfect to ~70%

   Class L's swing is the largest and has a specific, statable cause:
   only 60 distinct 12-feature vectors exist among the 200 L rows, so a
   10-fold group-aware split has roughly 6 groups per fold on average -
   too few for a stable estimate, which is exactly why the fold-to-fold
   variance is so high (some folds land 100%, one lands 43.88%). This is
   a genuine data-scarcity limitation (more diverse locker-ransomware
   samples would fix it), not a methodology flaw or a modeling failure.

   FOR THE PAPER: report 85.59% as headline accuracy. Report 98.10%
   explicitly labeled as a naive baseline inflated by duplicate-vector
   leakage, not silently replaced - the DELTA between the two numbers is
   itself a finding (a demonstrated, quantified example of why k-fold CV
   on small sandboxed security datasets needs group-awareness), arguably
   a stronger, more general contribution than either number alone.

2. THE AUTOENCODER WAS EVALUATED ON ITS OWN TRAINING DATA, AND WAS NEVER
   SEEDED (supersedes the 0.6069 F1 figure and the "TRUE FINAL retrain"
   entry's framing of the F1 fluctuation as unexplained)

   results/data_quality.json also found: train_autoencoder.py fits on
   goodware from balanced_dataset.csv; evaluate_autoencoder.py scores
   ransomware_dataset.csv. 100% of the distinct goodware vectors in that
   "evaluation" set are present in the training set. The reported 0.508
   mean goodware error, the 0.541678 threshold, and the 0.6069 F1 were
   all in-sample - not a held-out result, despite being reported as one.

   Separately, train_autoencoder.py never seeded numpy or TensorFlow.
   The F1 series reported across retrains in this file (0.70 -> 0.6216
   -> 0.7036 -> 0.6069) was, each time, attributed to a data or
   methodology change, with no control for how much was simply a
   different random initialization.

   scripts/autoencoder_variance_study.py fixes both at once: splits
   goodware ONCE (fixed random_state, reused across every seed) into 60%
   train / 20% threshold-calibration / 20% held-out test, never
   overlapping. Trains a fresh autoencoder per seed on the train split
   only, selects a threshold via percentile search on the calibration
   split, reports F1 on the held-out test split the model never touched
   during training or calibration - across 10 seeds.

   RESULT: held-out F1 = 0.6371 mean, std 0.0201, range 0.6124-0.6802.
   This study's seed-only range (0.0678) is 55% of the ENTIRE historical
   fluctuation range (0.1225) reported above. Meaning: roughly half of
   what looked like "the data changed, so F1 changed" across every
   retrain in this file was always just training-seed noise, with the
   same data and architecture held fixed. The other ~45% is likely a
   real effect of the data/methodology changes made each time - this
   study cannot separate which specific historical change contributed
   how much, only that seed noise alone explains a majority of the total
   swing.

   KNOWN LIMITATION, stated plainly rather than hidden: E/L (ransomware)
   rows are reused across the threshold-search step and the final-F1
   step, because only one ransomware dataset exists - splitting it
   further would leave too few samples for either step to be meaningful.
   This fixes the GOODWARE side of the contamination; the E/L reuse is a
   separate, acknowledged constraint, not fixed by this study.

   FOR THE PAPER: report F1 = 0.637 +/- 0.02 (10 seeds) as the corrected
   number, not a single run. Report the variance-decomposition finding
   (55% of historical fluctuation explained by seed noise alone) as its
   own result - it is a legitimate, general point about unseeded
   training in anomaly-detection retraining pipelines, not specific to
   this project.

3. THE LIVE DEMO'S CENTRAL CLAIM DOES NOT HOLD UP UNDER A NEGATIVE
   CONTROL (supersedes demo/DEMO_RUNBOOK.md's framing and
   bugs_debugs.txt FINDING #12's "not fixed, documented" status - this
   is now a bigger problem than FINDING #12 described)

   The demo runbook reports anomaly_score = 1.0 in all 3 pre-demo test
   runs and frames this as the autoencoder independently catching the
   simulated attack when the classifier (confused by system-wide
   dll_loaded noise, FINDING #12) reported Goodware - the dual-model
   defense-in-depth story. Nothing in that testing ever checked what the
   anomaly score looks like under the SAME conditions with NO attack
   running - the missing control.

   scripts/negative_control.py runs the real monitor stack (file,
   process, network, registry - same as production) against
   demo/victim_files/ (recreated via --setup for environment parity with
   the original 3 runs) for 35 seconds, but never invokes
   simulate_ransomware_behavior.py --attack. Ambient system activity
   (this machine's own background processes, the monitor's own ML
   library imports) is the only source of events.

   RESULT: label=G, confidence=86.1% (classifier correctly says
   goodware, as expected with zero attack) - but anomaly_score=280.47,
   is_anomaly=True. 280x the calibrated threshold, with no attack
   activity at all. This is only fully visible because of this
   project's C1/C2 fix (detect_anomaly() no longer caps the score at
   1.0 - see bugs_debugs.txt BUG #13's sibling fixes, tracked separately
   in the v2 branch); under the old capped code this would have been
   indistinguishable from a borderline case reading exactly 1.0.

   This directly contradicts the demo's framing: the SAME signal (in
   fact a far more extreme version of it) occurs with no attack at all,
   in the same environment. It does not distinguish attack from no-attack
   - it appears to fire on this environment's ambient noise regardless.
   Strongly supports FINDING #12's self-noise explanation, and escalates
   it: FINDING #12 as written treats the classifier's confusion as the
   problem and the autoencoder's CRITICAL alert as the system still
   working. This result says the autoencoder's CRITICAL alert may not be
   meaningfully attack-correlated at all in this environment.

   FOR THE PAPER: the "dual-model defense-in-depth, autoencoder catches
   what the classifier misses" framing cannot be used as currently
   written - it is not supported by this result. Recommended reframing:
   report the negative control as its own finding (a live system's
   anomaly-detection path can fire on the monitoring process's own
   resource footprint, independent of any attack - a genuine, general
   pitfall for host-based anomaly detection, not unique to this
   project), and either rerun the demo after implementing FINDING #12's
   proposed fix (excluding the monitor's own PID from process-monitor
   sampling) before claiming the dual-model result again, or drop the
   live-demo dual-model claim from the paper's results entirely and keep
   it only as a discussed limitation/future-work item.
